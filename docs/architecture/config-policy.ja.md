# 設定管理方針

## 基本方針

**Nix-first, Native-when-needed**

Home Manager を設定管理の中心とする。
Nix で自然に表現できる設定は原則として `.nix` で管理する。
Nix 化によって可読性・保守性・編集効率・機能性が低下する場合は、アプリケーション本来の設定形式を維持する。

一貫性・簡潔さ・美しさは、実用性を犠牲にしない範囲で追求する。

## 判断フロー

最初に当てはまる規則を適用する。

1. アプリケーションに構造化されたオプションを持つ `programs.*` または `services.*` がある場合は、それを使う。
2. 内容が構造化データ（TOML、JSON、YAML、KDL の値）の場合は Nix で宣言し、手書きの文字列ではなく `pkgs.formats.*` またはモジュールの `settings` で生成する。
3. 内容がコード（Nushell、Lua、シェル、Python）、または補完・LSP・フォーマッタが重要な形式の場合は、`xdg/` 配下にネイティブ形式で置き、モジュールから参照する。
4. アプリケーションが実行時に書き換えるファイルは、書き込み可能なファイルとして配置する（「書き込み可能・可変ファイル」を参照）。
5. 二つの選択肢の実用性が同等なら、より一貫性が高く簡潔なほうを選ぶ。

規則 2 と 3 の内部で迷うときは、次の六つの基準で決める。
順序は、互換性、編集効率、可読性、保守性、再利用性、複雑性とする。

1. **互換性**：アプリ固有の機能がすべて使えるままか。
2. **編集効率**：補完・LSP・フォーマッタを失わないか。
3. **可読性**：設定の意図がより明確になるか。
4. **保守性**：変更箇所や依存関係を把握しやすくなるか。
5. **再利用性**：共通設定や OS 別設定をより簡潔に表現できるか。
6. **複雑性**：管理のためだけの抽象化を増やさないか。

拡張子を `.nix` に変えるだけで、これらのどれも改善しない場合は移行ではない。

## 設計原則

### 1. Home Manager を中心とする

- アプリケーションの導入と有効化は Home Manager で管理する。
- 依存パッケージ、環境変数、OS 別の分岐は Nix で記述する。
- `programs.*` と `services.*` を優先し、Home Manager にモジュールがない場合は `xdg.configFile` を使う。
- 設定の配置と再現性は Home Manager が担う。

### 2. 静的な設定は Nix で管理する

- テーマ、フォント、ウィンドウ設定。
- 単純なキーバインドと動作オプション。
- 外部コマンドとツールの依存関係。
- OS・ホストごとの差異。

### 3. プログラムはネイティブ形式を維持する

- Nushell の関数とスクリプト（`.nu`）、Neovim の Lua、Yazi の Lua プラグイン。
- 複雑なアプリケーション固有の設定。
- ネイティブの補完・LSP・フォーマッタが有用なもの。

大量のネイティブコードを `extraConfig` や文字列リテラルに埋め込まない。
`xdg/` 配下のファイルとして置き、`source` または `builtins.readFile` で参照する。

### 4. 設定の正本は一箇所

- 同じ設定を Nix とネイティブファイルの両方で定義しない。
- すべてのアプリケーションは `home/modules/*.nix` から入る。
- ネイティブファイルは対応するモジュールから参照する。
- `~/.config/` 内の生成物は直接編集せず、Git 管理下のソースを変更する。

### 5. 宣言的設定と実行時の状態を分離する

Home Manager の出力は、読み取り専用の Nix store へのシンボリックリンクになる場合がある。

| 種別 | 管理方法 |
|---|---|
| 静的な設定 | Nix で宣言する |
| キャッシュ・履歴・セッション | アプリケーション側で管理する |
| アプリケーションが書き換える設定 | 書き込み可能なファイル（後述） |
| 秘密情報 | Git 管理の設定から分離する（「秘密情報」を参照） |

### 6. クロスプラットフォーム対応

macOS と Linux で設定を共有し、OS 固有の差異は Nix で分岐する。

```nix
lib.optionalAttrs pkgs.stdenv.isLinux {
  copy_command = "${pkgs.wl-clipboard}/bin/wl-copy";
}
```

- 共通設定の重複を避ける。
- OS 固有の依存関係を明示する。
- 環境依存のパス、ユーザー名、ホスト名をハードコードしない。

## 書き込み可能・可変ファイル

動作する範囲で、可変性が最も低い方式を選ぶ。

| 必要性 | 仕組み | 再現性 |
|---|---|---|
| アプリケーションがときどき書き込み、初期値を配れる | activation で同期する実ファイル | activation 時に初期化され、ローカルの編集は残る |
| 頻繁に手で編集し、変更ごとの rebuild が重い | 作業ツリー内のパスへの `config.lib.file.mkOutOfStoreSymlink` | 編集が即時反映される。ファイルは store の外になる |
| アプリケーションが完全に所有する | 管理しない。state または data ディレクトリに置く | 設計上なし |

実行時にパスを解決する仕組み（Bun が realpath から import を解決する場合など）も、store のシンボリックリンクではなく実ファイルか out-of-store のシンボリックリンクを必要とする。

## 秘密情報

- 秘密情報は agenix で管理し、暗号化ファイルは `secrets/` に置き、`secrets/secrets.nix` で鍵を対応づける。
- 平文の秘密情報や非公開の値はコミットしない。非公開の値は `local/` または state ディレクトリに置き、実行時に読む。
- 公開されるモジュールが宣言してよいのは秘密情報の配置先であり、中身ではない。

## アプリケーション別の方針

| アプリケーション | 管理方式 | 理由 |
|---|---|---|
| Zellij | Nix | 静的設定が中心。レイアウトが単純な設定を超えたらネイティブ KDL を維持する |
| Alacritty | Nix の設定とネイティブのヘルパー | TOML の設定は Nix で生成し、ヘルパースクリプトはネイティブのまま置く |
| Git | Nix | Home Manager との親和性が高い |
| Nushell | ハイブリッド | 関数やスクリプトは `.nu` が適切 |
| Neovim | ハイブリッド | Lua による設定とプラグイン管理 |
| Yazi | ハイブリッド | 静的設定と Lua プラグインを分離する |
| OpenCode | ハイブリッド | 静的設定と実行時の状態を分離する |

## ディレクトリ構成

```text
dotfiles/
├── flake.nix
├── hosts/
│   └── darwin/
├── home/
│   ├── default.nix
│   ├── packages.nix
│   └── modules/
├── nix/
├── secrets/
└── xdg/
    └── config/
```

- `home/modules/` をアプリケーション設定の唯一の入口とする。
- `hosts/` にはマシン単位（nix-darwin）の設定を置き、ホストごとの差異はモジュールではなくここに置く。
- `xdg/config/` には、ネイティブ形式で管理する意義のあるファイルだけを置く。

## 運用ルール

- 新しい設定は、まず Home Manager で管理できるか確認する。
- 既存設定は、保守性が実際に改善するものだけを段階的に移行する。
- 動作している設定を、美観だけのために書き換えない。
- ソースと生成物を明確に区別する。
- 同じ目的の仕組みを、理由なくアプリごとに混在させない。
- 新しい依存関係や抽象化には必要性を示す。

## 検証

リポジトリのルールに従い、ゲートは変更範囲に絞る。

| 変更 | ゲート |
|---|---|
| `.nix` ファイル全般 | `just fmt-check`、`just lint`、`just dead` |
| モジュールの出力が変わる変更 | ターゲット全体を評価し、変更した成果物をビルドする |
| 純粋なリファクタ | 変更前後で `.drvPath` がバイト単位で一致することを確認する |
| ネイティブファイル | その言語自身のチェック（Nushell なら `nu --ide-check 1000 <file>`） |

フォーマット・lint・未使用コード検出は設定を評価しないため、評価は別の手順として行う。

## 最終的な判断基準

美しい dotfiles とは、すべてが同じ形式で書かれたものではない。
各設定が適切な場所にあり、管理方法が一貫し、変更と再構築が容易なものである。

優先順位：

1. 正確性・機能性
2. 保守性・変更の容易さ
3. 再現性・移植性
4. 構成の一貫性
5. 簡潔さ・美しさ

実用性に差がない場合は、より一貫性が高く、簡潔で美しい構成を選ぶ。
